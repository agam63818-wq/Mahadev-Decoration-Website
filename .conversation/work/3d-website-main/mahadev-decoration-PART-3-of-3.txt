INSTRUCTIONS FOR THE CODING AGENT:
This is the final part of the same project (Part 1 = public site +
design system, Part 2 = booking engine + database + customer
dashboard). Do not redesign anything already built — reuse the same
design tokens, component system, and database schema. This part adds
the full admin/business-owner side of the platform, then finishes
with hardening, structure, and a pre-launch checklist.

────────────────────────────────────────────────────────────────
ADMIN ACCESS
────────────────────────────────────────────────────────────────
/admin/login — separate, restricted login (never reachable via public
sign-up; admin accounts are provisioned directly in Supabase/role
table). All /admin/* routes are auth + role gated server-side, not
just hidden client-side.

────────────────────────────────────────────────────────────────
ADMIN DASHBOARD OVERVIEW (/admin)
────────────────────────────────────────────────────────────────
Cards: Today's Events, Upcoming Events, Pending Inquiries, Confirmed
Bookings, Total Revenue, Advance Received, Pending Payments, Monthly
Growth — each pulling live data, each with a sensible loading
skeleton, each clickable through to the relevant admin section.

────────────────────────────────────────────────────────────────
CALENDAR (/admin/calendar)
────────────────────────────────────────────────────────────────
Month / Week / Day views. Each event chip shows customer, event type,
location, status — color-coded by status (reuse the same status→color
mapping as <BookingTimeline/> from Part 2 so customer and admin views
stay visually consistent). Clicking an event opens a detail side
panel (not a full page navigation) with quick actions.

────────────────────────────────────────────────────────────────
BOOKING MANAGEMENT (/admin/bookings)
────────────────────────────────────────────────────────────────
Filterable/sortable table (DataTable component) of all booking
requests/bookings. From a row or its detail panel, admin can: view
full inquiry, contact customer (click-to-call/WhatsApp with number
prefilled), edit booking details, change status (writes to
booking_status_history, triggers any relevant customer notification),
create/edit a quotation (see Quotation Manager below), assign team
members, record a payment, upload event-day photos, add internal
notes (never customer-visible unless explicitly marked so), and
cancel a booking (with a required reason, logged to history).

Quotation Manager (part of the booking detail panel): add/edit line
items (description, quantity, unit price, discount), auto-computed
total, set advance-required amount (auto-computes remaining), notes,
terms, validity date, then Send to Customer (status → "Quote Sent").
Reuses the same printable-PDF generation from Part 2.

────────────────────────────────────────────────────────────────
CUSTOMER MANAGEMENT (/admin/customers)
────────────────────────────────────────────────────────────────
Searchable customer list. Customer profile view: name, phone,
WhatsApp, email, full booking history, total spending, events
completed, internal admin notes.

────────────────────────────────────────────────────────────────
PAYMENT MANAGEMENT (/admin/payments)
────────────────────────────────────────────────────────────────
Overview of total expected revenue, total received, pending,
overdue, and refunds, plus a full transaction table filterable by
date, customer, payment status, and event type. Every figure here
must be derived from the real payments table (Part 2), never
hardcoded or estimated client-side.

────────────────────────────────────────────────────────────────
PORTFOLIO MANAGER (/admin/portfolio)
────────────────────────────────────────────────────────────────
Upload images and videos (including before/after pairs) into
portfolio_items/portfolio_media (Part 2 schema). Per item: title,
category, event type, location, price range, description, services
included, featured toggle, SEO metadata (title/description/alt
text), public/private toggle. This is what ultimately powers the
Part 1 gallery/homepage sections, so changes here must reflect live
on the public site without a redeploy.

────────────────────────────────────────────────────────────────
PACKAGE MANAGER (/admin/packages)
────────────────────────────────────────────────────────────────
Create/edit packages: starting price, inclusions list, images,
featured toggle, active/inactive toggle. Powers the Part 1
packages section/pages the same way.

────────────────────────────────────────────────────────────────
REVIEW MODERATION (/admin/reviews)
────────────────────────────────────────────────────────────────
Queue of submitted reviews: approve, reject, edit display settings,
mark featured. Only approved reviews appear on the public /reviews
page and homepage — enforce this via RLS/query filter, not just UI
hiding.

────────────────────────────────────────────────────────────────
ANALYTICS (/admin/analytics)
────────────────────────────────────────────────────────────────
Recharts-based charts: monthly bookings, revenue over time, popular
event categories, lead source breakdown, conversion rate (inquiry →
confirmed), repeat-customer rate, pending-payment trends. All derived
from real tables — label clearly if any metric is an estimate.

────────────────────────────────────────────────────────────────
SETTINGS (/admin/settings)
────────────────────────────────────────────────────────────────
Edit business_settings (phone, WhatsApp, address, hours, social
links), manage service_areas (add/remove/edit the areas shown on the
public Service Area section), manage team_members roster.

────────────────────────────────────────────────────────────────
ADMIN COMPONENT ADDITIONS
────────────────────────────────────────────────────────────────
AdminSidebar, AdminHeader, DataTable (sortable/filterable/paginated),
plus reuse of Modal/Toast/ConfirmDialog/LoadingState/EmptyState/
ErrorState from Part 1. Every destructive action (cancel booking,
reject review, delete portfolio item) goes through ConfirmDialog —
no silent deletes.

────────────────────────────────────────────────────────────────
FILE STRUCTURE
────────────────────────────────────────────────────────────────
Keep a clean, scalable structure across all three parts:
app/               — routes (public, dashboard, admin)
components/        — shared presentational components
features/          — feature-scoped logic (booking, quotations,
                     payments, portfolio, admin-*, etc.)
lib/               — Supabase client, utilities, constants
hooks/             — shared custom hooks
types/             — shared TypeScript types (mirror DB schema)
services/          — data-access layer (typed functions wrapping
                     Supabase queries — this is what Part 1's
                     "swap-in-later" data layer should now call)
utils/             — pure helper functions
supabase/          — migrations, RLS policies, edge functions
public/            — static assets
Keep business logic out of components; components stay presentational
and call into services/features.
