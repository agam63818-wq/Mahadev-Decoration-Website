## Chosen design

Native Web Push (VAPID) from a Node.js Vercel route, with subscriptions owned by existing `profiles` and a PostgreSQL per-booking/per-device durable queue. No LLM, paid push provider or second booking system.

A scheduled, authenticated worker discovers committed requests from the migration activation time, snapshots notification content from trusted database fields, fans out to registered staff devices, and leases pending delivery rows. This deliberately uses the booking table itself as the durable event source: **no notification trigger, external network call or push-table write runs inside the booking transaction**. A push outage cannot roll back bookings. Polling normally adds up to one minute of latency; schedule is mandatory, not an optional reliability enhancement.

The existing in-app bell is preserved. Push links reuse its exact request-detail route. A separate per-request idempotency key on the existing insert closes the prior duplicate-POST hole; this does not replace booking creation.

External push delivery is at-least-once, not magically exactly-once. Unique rows, leased attempts and browser-side event deduplication suppress normal retries; a provider-accepted send followed by process death can still be retried. Mobile/OS power policy and force-stopped browsers can prevent or delay delivery.

## Database rollout and security

1. Back up production and verify the live columns/policies against the inspection above. Apply to a staging copy first. The test fixture is deliberately minimal, not proof that production matches.
2. Ensure the existing alignment migrations through 0015 are already applied. Do not replay `schema.sql` or blindly replay the entire old migration history (there are duplicate historical migration numbers).
3. Apply **`supabase/migrations/0016_booking_push.sql` before deploying the new booking form/API**. Its `submission_key`/`submission_hash` columns must exist before keyed booking requests are sent. The migration is transactional and re-runnable.
4. It adds four RLS-enabled tables: `admin_push_subscriptions`, `booking_push_config`, `booking_push_events`, `booking_push_deliveries`. The singleton activation timestamp prevents historical-booking floods and does not reset on reapplication.
5. Registration/delivery RPCs are executable only by `service_role`. Browser clients can read only their own subscription rows if still staff; they cannot write the tables or read events/delivery logs. Next Server Actions verify the existing `getAdminUser()` before privileged access and derive the profile ID from the verified session.
6. The explicitly added `guard_profile_role` trigger blocks browser JWT role changes and non-customer self-provisioning. This closes a privilege escalation allowed by the old own-profile `FOR ALL` policy without deleting/changing that policy. Owner SQL/service-role provisioning remains available. Test any external profile provisioning integrations before rollout.
7. Worker targeting rechecks `profiles.role IN ('admin','team')`, matching the existing admin boundary. No email, single owner ID, or device is hard-coded.
8. Registration validates real P-256 key material. Sender destinations are allowlisted (FCM/Chrome, Mozilla, Apple); arbitrary HTTPS endpoints, IPs, credentials and custom ports are rejected to prevent SSRF. Add future providers deliberately after security review.

## Mandatory scheduler: Supabase Cron -> Vercel

Use the existing Supabase project rather than adding a push provider. In the Supabase dashboard, enable **Cron (`pg_cron`)**, **`pg_net`**, and **Vault**, if not already enabled. In Vault, save:

- `booking_push_worker_url`: `https://YOUR-CANONICAL-PRODUCTION-DOMAIN/api/internal/booking-push`
- `booking_push_worker_secret`: exactly the Vercel `CRON_SECRET`

Then run this once in that project's SQL Editor (check for an existing job first):

```sql
select jobid,jobname,schedule,active from cron.job where jobname='mahadev-booking-push';

select cron.schedule('mahadev-booking-push', '* * * * *', $job$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name='booking_push_worker_url'),
    headers := jsonb_build_object(
      'Content-Type','application/json',
      'Authorization','Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name='booking_push_worker_secret')
    ),
    body := '{}'::jsonb,
    timeout_milliseconds := 55000
  );
$job$);
```

This is an authenticated **POST** route, not an unauthenticated webhook and not a browser endpoint. No request payload is trusted. Supabase Cron runs every minute independent of open admin tabs. Vercel Cron is intentionally not added: per-minute schedules are plan-dependent, and Vercel cron uses GET. Configure one scheduler only. The canonical URL must not redirect; Vercel deployment protection must allow the production worker URL. This is manual environment configuration, **not already provisioned by the PR**.

The Node route has `maxDuration=60`, batches 10 deliveries with concurrency 5, and uses 5-second push transport timeouts. Check the target Vercel plan permits this duration. Each next scheduler invocation drains another batch. This is appropriate for current booking volume, not a bulk marketing system. Monitor backlog and scale the bounded batch/frequency if sustained traffic exceeds 10 device-deliveries/minute.

## Delivery and duplicate semantics

- Customer UI uses an opaque `Idempotency-Key` stable for identical data in the same tab for 24h, surviving refresh/retry through sessionStorage. Storage contains a digest/key, not the form. The **database unique index** is the authority. Changed data with an existing key returns 409. Successful replay returns the original reference. Requests from older clients without the header still work, but have no submission-level retry guarantee; new independent keys represent new bookings.
- The existing API remains the only booking insertion path. Existing customer linking, status flow and in-app bell insertion remain unchanged. The form now forwards the already-supported package/service/design IDs for correct trusted snapshots.
- The worker discovers requests from activation within the last 24h, and creates one event per `(booking_request_id, notification_type)`. It does not depend on the best-effort in-app bell insert, which might fail separately.
- Fanout is transactional, unique by `(event_id, subscription_id)`. With no valid devices, events wait up to 24h. Once fanout has happened, newly registered devices do not receive old events. Multiple admins and multiple devices are supported.
- `FOR UPDATE SKIP LOCKED`, five-minute leases and random lease tokens prevent parallel workers claiming the same active delivery. Success is never retried; an old token cannot acknowledge a newer lease.
- Timeouts, 429, 5xx and network errors retry exponentially (60s, 120s, etc.), up to 8 attempts / event expiry. `Retry-After` is respected with a 30s–6h bound. 401/403 preserve subscriptions because they can indicate bad VAPID configuration. 404/410 disable the endpoint. Invalid subscription data is disabled; invalid payload/400/413 is terminal.
- Events expire 24h after booking creation; offline browser delivery also has a provider TTL of up to 24h from accepted send. If the scheduler is down more than 24h, older bookings remain in the admin list but are **not replayed as stale push alerts**. Inspect the missing-event query below after an outage.
- `sent` / `accepted` means the push service accepted the request, **not** proof that the device displayed or the admin read it. Provider acceptance followed by acknowledgement failure is intrinsically ambiguous. Topic/tag + seven-day IndexedDB event IDs suppress repeat display where storage is available. This is not a mathematical exactly-once guarantee across OS/data resets.

## Service worker, click routing and device UX

Only `/sw.js` is registered, on explicit admin opt-in; it refuses to replace a different existing worker discovered at runtime. It is served without caching. Do not add another root worker. It has no fetch handler and never caches admin HTML/API/customer data.

The public `/manifest.webmanifest` is linked only from admin metadata, with existing brand-derived PNG icons. Admins can install from Chrome's Add to Home Screen / Install menu. Normal HTTPS Chrome can also receive push without installing. iOS support requires a compatible version and Home Screen installation; it was not physically tested here.

Settings contains Enable, current-device status, Refresh, Disable and Test. The test is admin-only, current-device-only, database-throttled to once/minute, and does not create bookings or affect statistics. Permission denied/dismissed, missing config, unsupported browser and network failures have explicit messages. Never auto-prompt a customer.

Click targets are derived from a UUID, not an arbitrary URL. The worker navigates/focuses an existing same-origin admin window, otherwise opens the exact `/admin/bookings?ref=<id>`. Middleware/login preserve the query string. Records older than the 200-row list are explicitly fetched using the existing service/mapping/modal. Deleted records show the existing unavailable state; query failures show retryable errors, not a false empty state. An offline click still needs connectivity to fetch the protected booking detail; no private offline cache is introduced.

Logout disables the current server record where reachable and unsubscribes the browser even if the server call fails. Log back in and explicitly Enable again. Session expiry without explicit logout does not automatically revoke an opted-in browser device; tapping its notification requires reauthentication. Other devices remain enabled. Demoted/deleted profiles stop future worker targeting. A send already accepted by the provider cannot be recalled. Only enable on trusted devices: customer name/event/location/package can appear on the lock screen.

## Monitoring, retention and troubleshooting

Owner/service-role SQL only; never expose these queries or keys in the browser:

```sql
select status,count(*) from public.booking_push_deliveries group by status;
select count(*) as no_device_events from public.booking_push_events
where expanded_at is null and expires_at>now();
select id,attempt_count,last_error,next_attempt_at from public.booking_push_deliveries
where status in ('failed','pending','sending') order by created_at desc limit 50;
-- Missing events after an outage (including requests older than retry horizon):
select b.id,b.created_at from public.booking_requests b
where b.created_at >= (select activated_at from public.booking_push_config where id)
  and not exists(select 1 from public.booking_push_events e where e.booking_request_id=b.id)
order by b.created_at desc limit 50;
select jobid,status,start_time,return_message from cron.job_run_details
order by start_time desc limit 10;
select id,status_code,timed_out,error_msg from net._http_response
order by id desc limit 10;
```

Cron job success only means the HTTP request was queued: also inspect `net._http_response`, Vercel worker logs and queue state. Alert if scheduler requests fail or oldest pending work exceeds five minutes. `http_401/403`: inspect matching VAPID key/subject. Worker 401: inspect Vault bearer secret. Worker 503: inspect migration/configuration/database access. No registered devices: use Settings. No display despite accepted push: inspect OS permission, browser battery/background limits, expiry and network. Never log raw subscription objects, provider error bodies or customer payloads.

Owner-approved retention example: delete terminal delivery/event records older than 30 days (events cascade deliveries), and disabled subscriptions inactive for 30 days. Keep booking records intact. After such retention the missing-event audit should be limited to the retained period. Do not blindly reset sent events for a retry: retry only selected failed rows, retaining their event ID, and only before expiry. Stop the scheduler to pause sending; stopping it does not affect bookings or the in-app bell.
